# 02 · Repeat Same Prompt

> 核心问题：**同一个前端需求重复生成，结果真的会稳定吗？**

状态：`COMPLETE`

所属章节：`No UI Harness`

上一节已经确认：

> 用户只给业务目标时，模型会主动补出大量前端决策。

现在只增加一个问题：

> **同一句完全相同的 Prompt，再生成一次，这些决定还会一样吗？**

---

## ① 只增加一个变量

上一节：

```text
Prompt
↓
Run 1
```

这一节：

```text
同一个 Prompt
├── Run 1
└── Run 2
```

两个 Run：

```text
同一个 Provider
同一个 Model
同一个 Prompt
同一个程序
不共享历史
```

唯一变化：

> **重新生成了一次。**

---

## ② 为什么 Run 之间不能共享历史？

如果这样做：

```text
Prompt
↓
Run 1
↓
把 Run 1 放进 Context
↓
Run 2
```

那第二次回答已经不是同一个实验条件。

所以这里每次都重新发送：

```text
messages = [
  { role: "user", content: "帮我做一个数据同步系统的前端" }
]
```

Run 1 和 Run 2 互相不知道对方存在。

---

## ③ 这一节仍然不加 Harness

不指定：

```text
Framework
UI Library
CSS
Design System
Tokens
组件
页面结构
目录
依赖
```

也不要求 JSON。

原因：

> 我们现在还只是观察“重新生成是否会改变决定”，不是统计具体漂移维度。

---

## ④ 运行

```bash
npm run openui:01:02
```

程序会原样打印：

```text
Run 1 · Model Output
Run 2 · Model Output
```

然后肉眼比较。

---

## ⑤ 比较什么？

重点看：

```text
技术方案
UI / CSS 方案
主题 / 颜色 / 字体 / 圆角
导航 / 页面布局
页面与业务模块
组件与交互
目录 / 依赖 / 代码组织
```

这一步只需要发现：

```text
相同
或
不同
```

不要统计：

```text
到底多少字段变了
哪些字段最容易漂
unique = 2/3
```

这些属于下一节：

```text
03 · Decision Drift
```

---

## ⑥ 这节真正想验证什么？

如果两个结果不同：

```text
同一个业务目标
+
没有 Harness
↓
前端决策可以重新采样
```

如果两个结果看起来很像，也不能马上证明稳定。

因为：

```text
两次相似
≠
这些决定已经属于 Product / Harness
```

这里只建立“重复生成”这个观察入口。

真正的结构化验证留到下一节。
